On February 2, 2025, Andrej Karpathy posted an important observation about AI programming on X and systematically introduced the concept of vibe coding.

The concept quickly attracted attention. Its appeal is that it lets developers program in a way similar to a product manager describing requirements to an engineering team and quickly receiving a prototype. It greatly improves the efficiency of prototype development. Karpathy described three core features:

1. **Intuition-driven and immediate feedback**: fully giving in to the vibes lowers the barrier to development and allows non-professional developers to build functional prototypes.
2. **Natural-language interaction**: natural language becomes the unified interface, breaking the barrier of traditional programming languages and changing the human-machine collaboration paradigm.
3. **Acceptance of code redundancy**: in rapid prototyping, code can be somewhat redundant or suboptimal. Speed matters more than quality, especially for throwaway weekend projects and proofs of concept.

## The Rise and Decline of Vibe Coding

With the spread of vibe coding, many startups emerged around this idea. Base44 was especially striking. From founding to acquisition, the company lasted only six months and was ultimately sold for $80 million. This showed how strongly capital chased the trend.

But problems soon appeared. A natural-language, intuition-driven interaction mode is inherently weak at precise requirement description. For long-term projects, this can damage stability, team collaboration, and maintainability. Companies dedicated to repairing the legacy of vibe-coded projects, such as Ulam Labs, have already begun to appear.

## The Rise of Spec Coding

Spec coding emerged as a response. Its core idea is that natural language alone is not enough. Requirements must be structured into specifications that can guide models, tests, implementation, and review.

In this paradigm, the human no longer only says "make me an app." The human defines constraints, behaviors, acceptance criteria, data models, interfaces, and edge cases. The AI then generates code within a clearer frame.

Spec coding therefore shifts the center of gravity. The asset is no longer just code. It is the specification that expresses intent.

## Spec Kit: Official Entry

When official tools such as Spec Kit appeared, the idea became more explicit. The software-development process began to move from prompt-driven generation toward spec-driven execution. This is not a rejection of AI coding. It is a maturation of AI coding.

The better the model becomes at generating code, the more important it becomes to define what should be generated. In the past, code was expensive and specifications were often treated as secondary documentation. In the AI era, code becomes cheaper and executable intent becomes more valuable.

## Anti-Consensus 1: Code Is No Longer the Core Barrier

The first anti-consensus is that code itself may no longer be the core moat. This sounds strange because software companies have long treated code as a central asset. But when AI can generate large amounts of code quickly, the differentiating value moves elsewhere.

The barrier may become product judgment, architecture, data, workflow understanding, domain knowledge, and the ability to define good specifications. Bad code can be regenerated. Bad product thinking cannot.

For industry AI applications, this is even more important. The value is not in producing code faster, but in translating domain complexity into a form that AI and software systems can execute.

## Anti-Consensus 2: Test-Driven Development Becomes More Important

The second anti-consensus is that test-driven development becomes more important, not less. If AI can generate code quickly, the limiting factor becomes verification. Tests express expected behavior. They protect the system from silent drift.

In traditional engineering, writing tests sometimes felt slower than writing code. In agent coding, code is cheap and mistakes are fast. Tests become the anchor.

## Anti-Consensus 3: Redefining Over-Engineering

The third anti-consensus is that over-engineering needs to be redefined. In the old world, building too much abstraction too early was a common failure mode. In the AI era, some structures that used to look heavy may become necessary.

Clear types, modular boundaries, acceptance tests, permission systems, and explicit specs may look like extra work. But when code generation accelerates, these structures prevent entropy. The question is not whether engineering is heavy. The question is whether the structure helps AI and humans collaborate safely.

## Conclusion

Vibe coding was an important breakthrough because it revealed the power of natural-language programming. But for professional systems, vibe alone is not enough. Spec coding may become the more durable paradigm.

When code is no longer the scarce resource, the scarce resource becomes clear intent. The future of AI-assisted engineering will belong to teams that can express that intent better than others.
