深度实践 Agent Coding 的工程团队往往会很快发现其对整体架构和标准软件工程提出的要求"不降反增"的现象。

这听起来有些反直觉——既然 AI 都能帮我写代码了，为什么还需要更严格的工程规范？但稍微想一想就明白了：当代码的产出速度从人均一天几百行提升到人均一天几千行时，如果没有好的模块化设计、类型约束、测试覆盖，那代码的腐败速度会远超以往。这就像给了一个厨神一把无限出菜的锅，但如果厨房的下水道堵了，他反而比原来更束手无策。

OpenAI 最近发布了关于 Codex App Server 的技术博客，完整分享了其如何将同一个 "harness" 复用到Web、CLI、IDE、macOS App等多个端——但本质上，它揭示了一个更深层的认知：好的系统设计，本质上是一种品味。

Codex的核心是一个"agent loop"：接收用户输入，调用模型推理，执行工具，反馈结果，循环迭代。这个逻辑听起来简单，但OpenAI花了大量精力将其"抽象"为一个稳定、可扩展的协议。他们称之为"App Server"——一个双向的JSON-RPC接口，既能接收客户端请求，也能主动向客户端"要"东西，比如执行前的审批确认。

真正让我触动的，是文章开篇的那句话："Initially, the App Server was a practical way to reuse the Codex harness across products that gradually evolved into our standard protocol."注意"evolved"这个词。不是"designed"，不是"architected"，而是进化。这意味着这个系统不是一开始就想清楚了，而是在做的过程中不断迭代、不断重构、不断提炼出来的。

笔者在最近的实践中逐渐体会到，一个真正好用的 Agent Coding 工作流，其复杂度可能远超很多团队最初的想象。以笔者自己的项目为例，光是让 AI 能够安全地操作代码库，就需要搭建一套包含如下组件的"脚手架"：

首先是 **Repo Context 注入系统**。你不能指望 AI 在每次交互时都能完整理解整个代码库——且不说 token 限制，光是传输成本就受不了。笔者目前使用的做法是维护一个增量索引，每次 git commit 后自动触发对变更文件的语义解析，用 Embedding 模型提取关键信息，存入向量数据库。AI 在开始工作前，先通过 RAG 从这个索引中检索相关的上下文。这套东西做下来，涉及的工具有：GitHub Actions（触发）、LangChain（编排）、Qdrant（向量存储），以及若干自写的 Python 脚本。听起来很重，但不做的话，AI 写的代码质量根本无法保证。

其次是 **多级沙箱执行环境**。Codex 在这一点上给了很好的示范：它会把 AI 生成的代码放到隔离的容器中运行，执行 shell 命令前会请求用户审批。这点在生产环境尤其重要。笔者目前采用了类似思路：用 Firecracker 搭建轻量级 VM，配合 gVisor 做容器隔离，每个月 AI 要执行的命令都需要经过策略引擎的审核。这不是过度谨慎——当 AI 可以直接执行 `rm -rf` 时，一个误操作就可能葬送整个项目。

然后是 **持续测试与回归检测**。这是最容易被忽视但也最关键的环节。AI 写代码很快，但如果缺乏快速验证的手段，那它的"快"反而会成为灾难。笔者目前的实践是：每个 PR 必须通过完整的单元测试 + 集成测试 + E2E 测试，才能合并到主分支。测试覆盖率的底线是 80%，低于这个阈值 CI 直接失败。这套机制听起来繁琐，但它让 AI 的每一次代码变更都能在几分钟内得到反馈——这就是我们前面提到的"反馈闭环"在工程层面的具象化。

最后是 **版本化的人类知识库**。这点往往被忽略，却是最体现"品味"的地方。AI 再强，它对业务的理解也来自于人类提供的上下文。这些上下文不能只是每次对话时临时塞给它的提示词，而应该被系统化地维护。笔者使用 MkDocs 搭建了一个文档站点，用 Git 管理，每次业务规则变更都需要更新对应的文档，然后通过自动化流程同步到 AI 的上下文中。这有点像是给 AI 写"宪法"——它是 AI 行为的边界，也是它理解业务的根源。

软件工程之所以是AI应用领域发展最快的赛道，原因只有一个：反馈闭环极短。

写一段代码，运行它，失败或成功，立刻知道结果。这个闭环可以是几秒钟。而如果你在做一个新药研发项目，从假设到实验到数据反馈，可能需要几周甚至几个月。反馈周期的差异，决定了进化速度的差异。

这正是《The Nature of Technology》一书中W. Brian Arthur所阐述的核心观点：技术是"组合进化"的。新的技术不过是在已有技术基础上的重新组合，而进化的动力来自于"需求-反馈-迭代"这个永动循环。Arthur甚至直言：技术从来不是"发明"出来的，而是"长"出来的。

有意思的是，DevOps运动在软件工程领域已经实践了十多年——持续集成、持续部署、自动化测试——这些本质上就是在压缩反馈周期。AI只是让这个过程变得不可忽视，甚至变得迫切。因为当AI Coding的速度从"天"提升到"分钟"时，如果你的CI/CD还是按"天"为单位运转，那就是整个系统的瓶颈。AI不是新事物，它只是让原本应该做的事情变得不得不做。

这种范式正在向其他领域扩散。

最近在bioRxiv上读到一篇来自LUMI-lab的论文，其核心逻辑让人振奋：他们构建了一个自驱动实验室（Self-Driving Laboratory, SDL），通过整合分子基础模型与自动化实验流程，在10轮迭代中合成了超过1700个LNP（脂质纳米颗粒），并在小鼠模型中实现了突破性的基因编辑效率。

最令人惊讶的还不是效率本身，而是系统自主发现了一个从未被文献报道过的特征：溴化脂质尾巴可以显著增强mRNA递送。这不是人类科学家"告诉"AI去探索的方向，而是AI在闭环实验中自主发现的新大陆。

这意味着什么？意味着LUMI-lab构建了一套科学版的App Server——一个能够接收假设、驱动实验、收集反馈、迭代假设的自动化循环。它不是某个单一工具，而是一个"驾驭系统"，让分子实验得以像代码一样快速迭代。

回到文章开头提到的"品味"。

笔者在实践中越来越体会到，搭建一个真正高效的技术系统，最困难的不是"实现功能"，而是设计那个循环本身。你需要思考：什么是输入？什么是输出？什么是反馈？如何判断一次迭代是"进步"还是"原地踏步"？

这些问题没有标准答案。不同的领域有不同的"原语"——Codex的原语是Item、Turn、Thread；LUMI-lab的原语是假设、实验、数据、模型；而一个组织管理系统的原语，可能是目标、行动、评估、调整。

持续重构的本质，不是不断推翻重来，而是不断提炼那个"循环"。

很多团队在引入AI后，第一反应是"用它来加速我们现有的流程"。但如果这个流程本身就是低效的、反馈周期很长的，那么AI做的不过是让一个慢的东西稍微快一点。真正有价值的工作，是在引入AI之前，先审视自己的流程是否足够"可迭代"。

这需要品味。

笔者从不怀疑AI会改变各行各业，但这个改变不会凭空发生。它需要有人去构建那个"harness"——那个驱动持续迭代的循环系统。软件工程已经走在了前面，不是因为这个领域更聪明，而是因为它天然拥有最短的反馈周期。

但周期是可以被压缩的。LUMI-lab证明了这一点。当自动化实验与AI模型结合时，科学研究的反馈周期可以被压缩到周级别甚至天级别。当你的企业流程被数字化、模块化、可观测化时，运营的反馈周期同样可以被压缩。

一切只是时间问题。

而在此之前，我们能做的，是培养自己的品味——知道什么样的系统值得构建，什么样的循环值得维护，以及什么时候该停下来审视，而不是盲目奔跑。方向错了，跑得越快，离目的地越远。
